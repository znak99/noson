# TODO 운영 가이드

## 1. 목적

이 문서는 Noson 프로젝트에서 사용자와 합의된 작업을 `TODO.md`에 빠짐없이 기록하고, 우선순위와 진행 상태를 일관되게 관리하기 위한 기준이다.

AI Agent는 TODO를 등록, 수정, 이동 또는 정리하기 전에 이 문서 전체와 현재 `TODO.md`를 반드시 확인한다.

## 2. 기본 원칙

- `TODO.md`는 사용자와 실행하기로 결정한 작업의 단일 목록이다.
- 사용자와 논의 중 실행하기로 결정된 모든 작업을 등록한다.
- 아직 결론이 나지 않은 아이디어, 단순 질문 또는 비교 후보는 작업으로 등록하지 않는다.
- 하나의 항목은 독립적으로 완료와 검증 여부를 판단할 수 있는 하나의 논리적 작업을 나타낸다.
- 서로 무관한 변경은 별도 항목으로 분리한다.
- 등록과 상태 이동은 실제 작업 상태와 동시에 갱신한다.
- 작업 설명과 진행 상황은 다른 AI Agent가 대화 기록 없이도 이어서 수행할 수 있을 만큼 구체적으로 작성한다.
- TODO 문서의 모든 설명은 한국어로 작성한다. 파일명, 코드 식별자 및 고유명사는 원래 표기를 유지할 수 있다.

## 3. TODO.md의 고정 구조

`TODO.md`에는 다음 3개 상태 섹션만 사용하며 순서와 제목을 바꾸지 않는다.

```markdown
## 미대응

## 진행중

## 완료
```

- `미대응`: 합의와 등록은 끝났지만 아직 착수하지 않은 작업
- `진행중`: 실제로 수행 중이거나 중단 후 재개를 기다리는 작업
- `완료`: 구현과 필요한 검증이 모두 끝난 작업

별도의 보류 섹션을 만들지 않는다. 중단되거나 외부 결정을 기다리는 작업도 진행중에 두고 상태를 구체적으로 기록한다.

## 4. 항목 필수 형식

모든 항목에는 다음 정보가 필요하다.

1. **한 줄 작업 설명**: 결과가 분명하게 드러나는 간결한 제목
2. **구체적인 설명**: 작업 범위, 기대 결과 및 필요한 경우 제외 범위

진행중 항목에는 `진행 상황`을 추가하고, 완료 항목에는 `완료 내용`과 `검증`을 추가한다.

### 4.1 미대응 형식

미대응 섹션은 우선순위 순서의 번호 목록을 사용한다.

```markdown
1. **한 줄 작업 설명**
   - 구체적인 설명: 작업 범위와 기대 결과를 작성한다.
2. **다음 작업 설명**
   - 구체적인 설명: 작업 범위와 기대 결과를 작성한다.
```

목록 번호는 고정 식별자가 아니라 현재 우선순위를 나타낸다. 작업을 추가하거나 이동한 뒤에는 `1`부터 빠짐없이 다시 번호를 매긴다.

### 4.2 진행중 형식

진행중 섹션은 불렛 목록을 사용한다.

```markdown
- **한 줄 작업 설명**
  - 구체적인 설명: 작업 범위와 기대 결과를 작성한다.
  - 진행 상황: 완료된 부분, 현재 수행 중인 부분과 다음 단계를 작성한다.
```

동시에 진행하는 작업 수는 실제로 병행할 필요가 있는 최소한으로 유지한다.

### 4.3 완료 형식

완료 섹션은 불렛 목록을 사용하며 최근 완료 항목을 위에 둔다.

```markdown
- **한 줄 작업 설명**
  - 구체적인 설명: 원래 작업 범위와 기대 결과를 작성한다.
  - 완료 내용: 실제로 반영된 결과를 작성한다.
  - 검증: 수행한 테스트, 분석, 비교 또는 수동 확인 결과를 작성한다.
```

단순히 `완료`라고만 쓰지 않는다. 구현 결과와 검증 근거를 보고 다른 Agent가 완료 여부를 판단할 수 있어야 한다.

## 5. 새 작업 등록 절차

사용자와 논의하여 작업이 결정되면 다음 순서로 등록한다.

1. 현재 `TODO.md`의 미대응, 진행중 및 완료 항목을 확인하여 중복 여부를 판단한다.
2. 기존 항목에 포함되는 작업이면 새 항목을 만들지 않고 구체적인 설명을 갱신할지 사용자에게 알린다.
3. 새 항목이면 의존성, 긴급도, 사용자 가치, 위험 및 현재 작업 흐름을 기준으로 우선순위를 판단한다.
4. 한 줄 작업 설명, 구체적인 설명 및 삽입 위치를 사용자에게 제안한다.
5. 반드시 “미대응 N번에 넣어도 될까요?”라는 형태로 사용자에게 우선순위를 제안한다.
6. 사용자가 동의하거나 다른 위치를 지정하면 미대응 섹션에 등록한다.
7. 삽입 후 전체 미대응 목록을 우선순위 순서로 다시 번호 매긴다.

제안 예시는 다음과 같다.

> “지정가 주문 상태 모델 정의” 작업은 백엔드 스키마와 체결 로직의 선행 작업이므로 미대응 2번에 넣어도 될까요?

사용자가 명시적으로 즉시 실행을 요청한 작업은 작업 수행 자체에 동의한 것으로 볼 수 있다. 이 경우에도 착수 전 메시지에서 등록 위치를 제안하고 TODO에 기록한다. 사용자가 다른 우선순위를 지정하면 그 지시를 따른다.

## 6. 작업 착수 절차

미대응 작업을 시작할 때는 코드나 문서를 수정하기 전에 다음 순서를 따른다.

1. 대상 항목이 현재 요청 범위와 일치하는지 확인한다.
2. 미대응에서 해당 번호 항목을 제거한다.
3. 남은 미대응 항목을 `1`부터 다시 번호 매긴다.
4. 같은 제목과 구체적인 설명을 진행중 섹션의 불렛 항목으로 이동한다.
5. `진행 상황`에 착수 시점의 현재 단계와 바로 수행할 내용을 작성한다.
6. 이후 의미 있는 단계가 끝나거나 작업이 중단되면 진행 상황을 갱신한다.

등록과 동시에 즉시 착수하는 작업도 개념적으로는 `미대응 등록 → 진행중 이동` 순서를 따른다. 최종 TODO에는 현재 상태만 남아도 되지만, Agent는 이 생명주기를 생략한 것으로 취급해서는 안 된다.

## 7. 작업 중단 및 재개

작업이 완료되지 않은 상태에서 중단되면 진행중 섹션에 그대로 유지한다. `진행 상황`에는 최소한 다음을 기록한다.

- 완료된 부분
- 남은 부분
- 중단 또는 차단 원인
- 확인한 오류나 위험
- 다시 시작하기 위한 조건 또는 다음 명령/파일/결정

중단 기록 예시는 다음과 같다.

```markdown
- **GMO Coin WebSocket 시세 구독 구현**
  - 구체적인 설명: 5개 지원 종목의 실시간 Bid, Ask, Last 데이터를 구독하고 Riverpod 상태로 제공한다.
  - 진행 상황: WebSocket 연결과 메시지 파싱까지 완료했다. 재연결 테스트는 GMO Coin 연결 제한 확인이 필요해 중단되었다. 공식 제한을 확인한 뒤 백오프 정책을 결정하고 테스트를 재개한다.
```

재개할 때는 기존 기록을 먼저 읽고 현재 코드 및 외부 상태와 일치하는지 확인한 뒤 진행 상황을 갱신한다.

## 8. 작업 완료 절차

다음 조건을 모두 충족한 후 진행중 항목을 완료로 이동한다.

1. 합의된 작업 범위가 모두 반영되었다.
2. 작업 위험에 맞는 테스트, 분석 또는 수동 검증이 끝났다.
3. 관련 문서와 현재 구현이 일치한다.
4. 실패한 검증이나 남은 위험이 숨김없이 기록되었다.
5. 남은 내용이 독립 작업이라면 사용자와 우선순위를 논의해 별도 미대응 항목으로 등록했다.

완료 이동 방법은 다음과 같다.

1. 진행중에서 대상 불렛 항목을 제거한다.
2. 완료 섹션의 맨 위에 같은 제목과 구체적인 설명을 추가한다.
3. `완료 내용`에 실제 변경 결과를 작성한다.
4. `검증`에 실행한 검증과 결과를 작성한다.
5. 완료 후 전체 TODO의 섹션, 목록 형식 및 번호를 확인한다.

부분 완료 상태에서는 완료로 이동하지 않는다. 범위가 의도적으로 축소되었다면 먼저 사용자와 새 완료 기준을 합의하고 구체적인 설명을 수정한다.

## 9. 우선순위 판단 기준

미대응 목록에서 번호가 작을수록 우선순위가 높다. 다음 기준을 종합하여 판단한다.

1. 다른 작업이 시작되기 위해 먼저 필요한 의존 작업
2. 실제 금융거래로 오인되거나 자산 데이터가 잘못되는 것을 막는 안전 작업
3. 출시 가능성을 조기에 검증하는 외부 약관, API 및 플랫폼 위험
4. MVP 핵심 사용자 흐름을 완성하는 작업
5. 장애, 데이터 손상 또는 보안 위험을 줄이는 작업
6. 품질 개선, 편의 기능 및 선택적 정리 작업

우선순위가 비슷하면 더 작고 검증 가능한 작업을 먼저 제안한다. 사용자 지정 우선순위는 이 판단보다 우선한다.

## 10. 변경 범위와 Git 관계

- TODO 항목 하나가 항상 커밋 하나와 일치할 필요는 없지만, 커밋 하나에는 하나의 논리적 변경만 포함한다.
- 하나의 TODO가 여러 독립 커밋으로 나뉘면 진행 상황에 완료된 단위를 기록한다.
- Git 작업 전에는 반드시 `docs/GIT_STRATEGY_S1.md`를 확인한다.
- TODO 상태 변경은 해당 구현 또는 문서 변경과 같은 논리적 작업에 포함한다.
- 관련 없는 TODO 정리는 현재 작업의 커밋에 섞지 않는다.

## 11. 자체 검증 체크리스트

TODO를 변경한 후 다음을 확인한다.

- [ ] 섹션이 `미대응`, `진행중`, `완료` 세 개이고 순서가 맞는가?
- [ ] 미대응 항목이 우선순위 순 번호 목록인가?
- [ ] 진행중과 완료 항목이 불렛 목록인가?
- [ ] 모든 항목에 한 줄 작업 설명과 구체적인 설명이 있는가?
- [ ] 진행중 항목에 실제 현재 상태가 구체적으로 기록되었는가?
- [ ] 중단 작업에 완료 부분, 남은 부분, 원인 및 재개 조건이 있는가?
- [ ] 완료 항목에 완료 내용과 검증 결과가 있는가?
- [ ] 동일하거나 겹치는 작업이 중복 등록되지 않았는가?
- [ ] 미대응 번호가 `1`부터 연속되는가?
- [ ] 사용자와 합의된 작업이 누락되지 않았는가?
