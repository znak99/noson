# Cloudflare 지정가 주문 백엔드 타당성 검증

## 1. 문서 목적

이 문서는 앱 종료 중 지정가 주문을 판정하는 Noson의 Cloudflare Workers, D1 및 Cron 구성이 무료 한도와 개발·운영비 `¥0` 원칙을 만족할 수 있는지 검증한다.

- 확인일: 2026-08-14 JST
- 확인 범위: Cloudflare 공식 Workers·D1 문서, 현재 Noson 시스템 설계 및 사용자 확정 사항
- 대상 기능: 지정가 주문 등록·취소·동기화, 5개 종목의 1분봉 조회, 미체결 주문 판정과 결과 보존
- 제외 범위: 실제 거래, 일반 시장 데이터 중계, 서버 포트폴리오 계산 및 회원 계정

## 2. 결론

다음 조건을 지키면 1,000 DAU 규모까지는 Cloudflare 무료 범위에서 충분한 여유를 두고 운영할 수 있다.

1. 단일 Cron을 매분 실행하되 `BTC`, `ETH`, `XRP`, `SOL`, `DOGE` 중 한 종목만 순환 처리한다.
2. 각 종목은 5분마다 처리하며 앱 종료 중 체결 결과 반영은 최대 약 5분 지연될 수 있다.
3. 마지막으로 처리한 1분봉 시각을 종목별로 저장하고 다음 실행에서 누락된 봉을 순서대로 처리한다.
4. Installation ID당 미체결 지정가 주문은 최대 20개로 제한한다.
5. 체결·취소 결과는 앱의 수신 확인 후 7일, 미확인 상태에서는 최대 90일 보존한다.
6. 전체 미체결 주문을 순회하지 않고 종목·매수/매도·상태·가격 범위에 맞는 인덱스로 이번 봉에 체결 가능한 주문만 처리한다.
7. 실제 Worker 구현에서 CPU 시간과 D1의 `rows_read`, `rows_written`, 저장 크기를 측정하고 운영 임계값을 넘으면 신규 주문부터 제한한다.

동일한 부하 가정에서 100 DAU와 1,000 DAU는 여유가 있지만 10,000 DAU는 Workers 일일 요청과 D1 일일 쓰기 한도를 초과한다. 따라서 현재 구조를 10,000 DAU용으로 간주하지 않는다. 유료 전환은 자동으로 수행하지 않으며 무료 범위를 벗어나면 기능 축소 또는 구조 재검토를 사용자와 결정한다.

## 3. 사용자 확정 사항

2026-08-14에 다음 사항을 확정했다.

- 단일 Worker와 단일 Cron을 사용하고 오프라인 지정가 체결에 최대 약 5분의 지연을 허용한다.
- Installation ID당 미체결 지정가 주문 상한은 20개다.
- 체결·취소 결과는 앱 확인 후 7일, 미확인 상태에서는 최대 90일 보존한다.
- 90일을 넘겨 복귀해 서버 결과를 복구할 수 없는 앱에는 동기화 만료를 안내하고 포트폴리오 초기화 경로를 제공한다.

## 4. 공식 무료 한도

### 4.1 Workers 및 Cron

[Workers Limits](https://developers.cloudflare.com/workers/platform/limits/)와 [Workers Pricing](https://developers.cloudflare.com/workers/platform/pricing/)에서 확인한 무료 한도는 다음과 같다.

| 항목 | 무료 한도 | 초과 또는 제약 |
|---|---:|---|
| Worker 요청 | 100,000회/일 | 자정 UTC에 초기화, 초과 시 오류 `1027` |
| CPU 시간 | 호출당 10ms | 지속 초과 시 호출 종료와 오류 `1102` |
| 메모리 | isolate당 128MB | 초과 시 실행 취소 가능 |
| 외부 subrequest | 호출당 50회 | 리다이렉트도 각각 집계 |
| D1 등 내부 서비스 subrequest | 호출당 1,000회 | 무료 D1 쿼리는 별도 50개 제한 적용 |
| 동시 외부 연결 | 호출당 6개 | 일곱 번째 연결은 대기 |
| Cron Trigger | 계정당 5개 | Noson은 1개만 사용 |
| Cron wall time | 호출당 15분 | CPU 한도와 별개 |

I/O 대기 시간은 CPU 시간에 포함되지 않지만 응답 JSON 파싱, 주문 판정, D1 결과 직렬화 같은 실제 계산은 CPU를 사용한다. 공식 문서는 일반 Worker의 평균 CPU 사용량을 약 2.2ms로 설명하지만 Noson의 실제 KLine 응답 크기와 D1 작업은 구현 후 별도로 측정해야 한다.

[Cron Triggers](https://developers.cloudflare.com/workers/configuration/cron-triggers/)는 UTC 기준으로 실행되며 설정 변경 전파에 최대 15분이 걸릴 수 있다. Cron 호출도 Worker 사용량 산정에 포함해 보수적으로 계산한다.

### 4.2 D1

[D1 Pricing](https://developers.cloudflare.com/d1/platform/pricing/), [D1 Limits](https://developers.cloudflare.com/d1/platform/limits/) 및 [D1 FAQ](https://developers.cloudflare.com/d1/reference/faq/)에서 확인한 무료 한도는 다음과 같다.

| 항목 | 무료 한도 | 초과 또는 제약 |
|---|---:|---|
| 읽은 행 | 5,000,000행/일 | 자정 UTC까지 D1 쿼리 불가 |
| 쓴 행 | 100,000행/일 | 자정 UTC까지 D1 쿼리 불가 |
| 계정 전체 저장 | 5GB | 공간 정리 전 신규 쓰기·DDL 불가 |
| 단일 DB 크기 | 500MB | 행 삭제 또는 DB 분할 필요 |
| DB 수 | 계정당 10개 | MVP는 단일 DB 사용 |
| Worker 호출당 쿼리 | 50개 | batch 내부 각 문장에도 개별 제한 적용 |
| SQL 쿼리 시간 | 최대 30초 | 큰 작업은 분할 필요 |
| Time Travel | 7일 | 장기 백업 수단으로 간주하지 않음 |

D1은 쿼리 결과 행 수가 아니라 실제로 읽거나 쓴 행 수를 집계한다. 인덱스가 없는 필터는 반환 행이 적어도 전체 스캔을 발생시킬 수 있다. 인덱스는 읽은 행을 줄이지만 인덱스 대상 열을 쓸 때 인덱스 행 쓰기가 추가된다.

단일 D1 DB는 쿼리를 한 번에 하나씩 처리한다. 과도한 동시 요청은 대기열에 들어가고 대기열까지 차면 overloaded 오류가 발생한다. 읽기 전용 쿼리는 재시도 가능한 오류에서 D1이 최대 두 번 자동 재시도하지만 쓰기는 멱등성을 보장한 뒤 지수 백오프와 jitter로 제한적으로 재시도해야 한다.

## 5. 확정 백엔드 처리 구조

### 5.1 Cron과 시장 데이터

Cron 표현식은 `* * * * *` 하나만 사용한다. 실행 시각의 분을 기준으로 한 종목을 결정한다.

| 분 인덱스 | 처리 종목 |
|---:|---|
| `minute % 5 == 0` | `BTC` |
| `minute % 5 == 1` | `ETH` |
| `minute % 5 == 2` | `XRP` |
| `minute % 5 == 3` | `SOL` |
| `minute % 5 == 4` | `DOGE` |

각 실행은 다음 순서를 따른다.

```text
Cron 1회 실행
  → 이번 분의 대상 종목 1개 결정
  → 해당 종목 KLine 조회
  → D1의 종목별 마지막 처리 봉 시각 조회
  → 아직 처리하지 않은 완료 1분봉을 시각 순으로 선택
  → 각 봉의 Low로 지정가 매수, High로 지정가 매도 조건 판정
  → 체결 가능한 미체결 주문만 원자적으로 상태 변경
  → 마지막 성공 처리 봉 시각 갱신
```

한 종목은 5분마다 처리되므로 정상 상태에서 새 1분봉은 최대 5개다. 예상 D1 문장은 체크포인트 조회 1개, 봉별 매수·매도 범위 처리 최대 10개, 체크포인트 갱신 1개로 총 12개이며 무료 호출당 50개 제한 안에 있다.

일본시간 06:00의 GMO Coin KLine 날짜 전환 또는 장애 복구 시에는 체크포인트가 가리키는 이전 날짜와 현재 날짜를 모두 조회할 수 있다. 외부 조회는 보통 1회, 경계 복구 시 2회로 Workers 무료 subrequest 50회보다 충분히 작다.

Cron 자체의 실행 보장이나 즉시 재시도에 의존하지 않는다. 실패하면 체크포인트를 갱신하지 않고 다음 해당 종목 실행에서 누락 봉을 다시 처리한다. 오래 누락된 경우 한 번에 처리할 봉 수를 제한하고 여러 실행으로 나눠 CPU와 쿼리 수 상한을 지킨다.

### 5.2 주문 조회와 원자성

다음 조회 패턴을 지원하는 최소 인덱스를 사용한다.

- Installation ID와 멱등성 키에 대한 주문 생성 중복 확인
- Installation ID별 미체결 주문 수 확인과 20개 상한 적용
- Installation ID와 갱신 커서에 따른 결과 동기화
- 종목·상태·매수/매도·지정가 범위에 따른 체결 후보 조회

미체결 주문만 포함하는 partial index를 우선해 읽기와 쓰기를 줄인다. 전체 주문 스캔, 종목 전체 스캔 및 앱의 반복 전체 동기화를 허용하지 않는다.

여러 상태 변경은 D1의 [batch API](https://developers.cloudflare.com/d1/worker-api/d1-database/)를 사용해 트랜잭션으로 처리한다. 주문 상태와 체크포인트를 같은 성공 단위로 다뤄, 일부 주문만 체결되고 체크포인트가 앞으로 이동하거나 같은 봉이 중복 적용되지 않게 한다. 상세 SQL과 취소·체결 경합 규칙은 백엔드 구현 작업에서 테스트와 함께 확정한다.

### 5.3 결과 보존과 정리

- 미체결 주문은 사용자가 취소하거나 체결될 때까지 보존한다.
- Installation ID 하나가 동시에 보유할 수 있는 미체결 주문은 최대 20개다.
- 앱이 체결·취소 결과를 로컬 자산에 반영하고 수신 확인을 보내면 `acknowledged_at`을 기록한다.
- 수신 확인된 결과는 7일 후 삭제한다.
- 수신 확인되지 않은 결과는 체결 또는 취소 후 최대 90일 보존한다.
- 정리 작업은 별도 Cron을 추가하지 않고 매분 Cron의 제한된 일부에서 작은 batch로 수행한다.
- 90일 후 결과가 삭제된 설치본이 복귀하면 임의로 체결 결과를 추측하지 않는다. 일본어로 동기화 만료를 알리고 포트폴리오 초기화 경로를 제공한다.

## 6. 사용량 산정

### 6.1 공통 부하 가정

DAU를 `N`으로 두고 활성 Installation ID 하나가 하루에 다음 작업을 수행한다고 가정한다.

| 작업 | 1인당 횟수/일 | 비고 |
|---|---:|---|
| 지정가 주문 생성 | 2회 | 멱등성 확인과 미체결 상한 확인 포함 |
| 지정가 주문 취소 | 1회 | 나머지 1회는 체결된다고 가정 |
| 결과 동기화 | 12회 | 활성 시간 동안 시간당 1회 수준의 보수적 가정 |
| Cron | 전체 1,440회 | 매분 1회, 사용자 수와 무관 |

실제 출시 전 부하 시험에서는 더 높은 burst, 악의적 반복 요청 및 장기 미접속 설치본을 별도로 검증한다.

### 6.2 Workers 요청

하루 Worker 호출 추정식은 다음과 같다.

```text
Worker 요청 = Cron 1,440 + N × (생성 2 + 취소 1 + 동기화 12)
            = 1,440 + 15N
```

| DAU | 요청/일 | 무료 한도 사용률 | 판단 |
|---:|---:|---:|---|
| 100 | 2,940 | 2.94% | 여유 |
| 1,000 | 16,440 | 16.44% | 여유 |
| 10,000 | 151,440 | 151.44% | 초과 |

요청 수만 보면 이론상 약 6,570 DAU에서 100,000회에 도달한다. 80% 운영 상한을 적용하면 약 5,237 DAU지만 D1 쓰기, 저장 공간, burst와 오남용을 함께 고려하므로 이를 보장 용량으로 사용하지 않는다.

### 6.3 D1 읽은 행

다음 보수적 계획값을 사용한다.

- 주문 생성 1회: 인덱스 조회 2행
- 주문 취소 1회: 인덱스 조회 1행
- 동기화 1회: 최대 20행 페이지 조회
- Cron: 실행당 체크포인트 1행과 하루 평균 사용자당 체결 후보 1행

```text
D1 읽은 행 = N × (생성 2회 × 2 + 취소 1 + 동기화 12회 × 20 + 체결 후보 1)
            + Cron 체크포인트 1,440
            = 246N + 1,440
```

| DAU | 읽은 행/일 | 무료 한도 사용률 | 판단 |
|---:|---:|---:|---|
| 100 | 26,040 | 0.52% | 여유 |
| 1,000 | 247,440 | 4.95% | 여유 |
| 10,000 | 2,461,440 | 49.23% | 산정상 한도 이내 |

이 계산은 적절한 인덱스가 실제로 사용된다는 전제다. 구현 시 각 쿼리의 D1 `meta.rows_read`와 `EXPLAIN QUERY PLAN`을 확인하지 못하면 이 판단은 무효다.

### 6.4 D1 쓴 행

주문 행과 3개 계획 인덱스를 고려해 생성은 주문당 4행 쓰기, 상태 변경은 주문 행과 영향을 받는 2개 인덱스를 고려해 주문당 3행 쓰기로 추정한다. Cron 체크포인트는 실행당 1행 쓰기로 계산한다.

```text
D1 쓴 행 = N × (생성 2회 × 4 + 취소 1회 × 3 + 체결 1회 × 3)
           + Cron 체크포인트 1,440
           = 14N + 1,440
```

| DAU | 쓴 행/일 | 무료 한도 사용률 | 판단 |
|---:|---:|---:|---|
| 100 | 2,840 | 2.84% | 여유 |
| 1,000 | 15,440 | 15.44% | 여유 |
| 10,000 | 141,440 | 141.44% | 초과 |

80% 운영 상한은 산정상 약 5,611 DAU다. 실제 인덱스 구성에 따라 쓰기 수가 달라지므로 배포 전 fixture 부하 시험과 D1 `meta.rows_written`으로 다시 계산한다.

### 6.5 저장 공간

스키마가 확정되지 않았으므로 주문 행과 인덱스를 합쳐 주문당 1KiB를 보수적 계획값으로 사용한다. 실제 크기는 fixture를 삽입한 D1에서 페이지 크기와 DB 크기로 측정한다.

| DAU | 모두 7일 내 확인 시 약 34행/인 | 90일 미확인 최악 약 200행/인 | 단일 DB 500MB 판단 |
|---:|---:|---:|---|
| 100 | 3.3MiB | 19.5MiB | 여유 |
| 1,000 | 33.2MiB | 195.3MiB | 여유 |
| 10,000 | 332.0MiB | 1,953.1MiB | 최악 시 초과 |

34행은 미체결 주문 상한 20개와 최근 7일간 하루 2개 결과 14개를 합친 값이다. 200행은 미체결 주문 20개와 90일간 하루 2개 미확인 결과 180개를 합친 값이다. 1,000 DAU의 최악 가정에서도 약 39%이므로 MVP 목표로 타당하다.

## 7. 운영 임계값과 한도 초과 동작

### 7.1 관측 항목

[Workers Metrics](https://developers.cloudflare.com/workers/observability/metrics-and-analytics/), [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/) 및 [D1 Metrics](https://developers.cloudflare.com/d1/observability/metrics-analytics/)에서 다음 항목을 확인한다.

- Worker 요청 수, 오류율, `1027`, `1102`, CPU p50·p95·p99
- Cron 성공·실패와 종목별 마지막 처리 봉 시각
- D1 `rows_read`, `rows_written`, DB 크기, 쿼리 지연 및 overloaded 오류
- 주문 생성·취소·체결·동기화 실패와 90일 만료 건수
- GMO Coin 응답 오류, 지연, 누락 봉 및 마지막 성공 조회 시각

Workers Free의 로그 이벤트는 200,000개/일과 3일 보존 범위다. 정상 호출마다 여러 상세 로그를 남기지 않고 오류, Cron 요약 및 표본 로그만 기록한다. 장기 사용자 행동 분석이나 외부 유료 로그 서비스를 도입하지 않는다.

### 7.2 임계값

| 자원 | 경고 | 신규 주문 제한 검토 | 공식 한도 |
|---|---:|---:|---:|
| Worker 요청/일 | 70,000 | 80,000 | 100,000 |
| D1 읽은 행/일 | 3,500,000 | 4,000,000 | 5,000,000 |
| D1 쓴 행/일 | 70,000 | 80,000 | 100,000 |
| 단일 DB 저장 | 350MB | 400MB | 500MB |
| Worker CPU p95 | 7ms | 8ms | 10ms/호출 |

경고 단계에서는 인덱스, 동기화 빈도, 비정상 반복 요청 및 미확인 결과 정리를 확인한다. 제한 단계에서는 신규 지정가 주문부터 일시 중단하고 기존 주문의 취소, 체결 판정 및 결과 동기화를 우선한다. 유료 플랜으로 자동 전환하지 않는다.

### 7.3 오류 처리

- Worker 일일 요청 한도를 넘으면 `1027`이 발생한다. 주문 API는 fail closed로 운영하고 앱은 일본어로 일시 중단과 재시도 가능 시점을 알린다.
- D1 일일 읽기·쓰기 한도를 넘으면 자정 UTC, 즉 일본시간 09:00까지 쿼리가 실패할 수 있다. 앱은 로컬 요청을 확정 체결로 오인하지 않고 pending 상태로 보존한다.
- CPU 한도 초과 `1102`가 발생한 Cron은 체크포인트를 전진시키지 않아 다음 실행에서 재처리한다.
- transient D1 오류만 멱등성 확인 후 제한 재시도한다. 한도 초과, 잘못된 SQL 및 저장 공간 초과는 즉시 재시도하지 않는다.
- 단일 DB가 500MB에 가까워지면 확인 완료 결과와 만료 결과를 먼저 정리한다. DB 분할은 읽기·쓰기 계정 한도를 해결하지 못하므로 MVP의 자동 대응으로 사용하지 않는다.

## 8. 구현·출시 게이트

Cloudflare 백엔드 구현과 출시 전에 다음을 모두 통과해야 한다.

1. 실제 GMO Coin KLine fixture와 D1을 사용한 Worker에서 Cron CPU p95가 7ms 이하이고 호출당 최대 10ms 초과가 재현되지 않는다.
2. 최대 5개 누락 봉과 주문 burst를 처리해도 D1 쿼리가 호출당 50개 이하다.
3. `EXPLAIN QUERY PLAN`에서 주문 생성, 동기화 및 체결 후보 쿼리가 의도한 인덱스를 사용한다.
4. D1 응답 `meta`로 시나리오별 실제 읽기·쓰기 행을 측정해 이 문서의 계획값을 교체한다.
5. 생성·취소·체결 경합과 Cron 재실행에서 같은 주문이 두 번 체결되지 않는다.
6. 7일 확인 결과, 90일 미확인 결과, 20개 미체결 상한 및 동기화 만료 흐름을 테스트한다.
7. Worker 요청과 D1 사용량이 80% 임계값에 도달했을 때 신규 주문이 중단되고 기존 주문 동기화가 보존된다.
8. GMO Coin의 제3자 앱 재표시와 Cloudflare 정기 조회에 대한 서면 허용을 확보한다.

CPU 또는 실제 D1 사용량이 게이트를 통과하지 못하면 이 구성을 출시 가능한 것으로 간주하지 않는다. 기능을 축소하거나 시장 데이터 처리 방식을 다시 설계하고 사용자와 결정한다.
