# GIT_STRATEGY_S1

## 1. 목적

`S1`은 소규모 프로젝트, MVP, PoC, 빠른 출시가 중요한 프로젝트에 적용하는 가장 단순한 Git 전략이다.

> 이 문서는 1인 개발 및 100% AI Agent 기반 개발 환경을 전제로 한다.
> Git은 협업자 간 커뮤니케이션보다 변경 이력 추적, 작업 단위 분리, 검증, 복구, 릴리스 안정성 확보를 위한 통제 장치로 사용한다.


핵심 목표는 `develop` 브랜치 없이도 `main`을 항상 릴리스 가능한 상태로 보호하면서, 모든 변경을 작업 브랜치와 PR을 통해 통제하는 것이다.

## 2. 핵심 원칙

- `main`은 항상 릴리스 가능한 안정 상태를 유지한다.
- `develop` 브랜치는 사용하지 않는다.
- 모든 추가, 수정, 리팩터링, 문서 작업은 `main`에서 작업 브랜치를 생성하여 수행한다.
- 작업 브랜치의 변경은 반드시 PR을 통해 `main`에 병합한다.
- `main`에 대한 직접 commit/push는 금지한다.
- 릴리스 시 필요에 따라 Git Tag를 생성한다.

## 3. 브랜치 모델

```text
main
 ├─ feature/*
 ├─ fix/*
 ├─ refactor/*
 ├─ chore/*
 ├─ docs/*
 └─ test/*
      │
      └── PR ──> main
```

## 4. 브랜치 역할

### `main`

- 릴리스용 브랜치
- 항상 배포 가능한 상태 유지
- 미완성 기능, 실험 코드, 임시 변경 금지
- 직접 commit/push 금지
- PR을 통해서만 변경

### 작업 브랜치

모든 일반 개발 작업은 `main`에서 작업 브랜치를 생성하여 수행한다.

작업 완료 후 PR을 생성하여 `main`에 병합한다.

## 5. 브랜치 네이밍

| Prefix | 용도 |
|---|---|
| `feature/` | 신규 기능 |
| `fix/` | 일반 버그 수정 |
| `refactor/` | 구조 개선 |
| `chore/` | 설정, 의존성, 유지보수 |
| `docs/` | 문서 작업 |
| `test/` | 테스트 작업 |

예시:

```text
feature/image-picker
fix/camera-permission
refactor/image-processor
chore/update-flutter
docs/update-readme
test/stereogram-generator
```

`hotfix/`와 `temp/`는 S1의 표준 정책으로 사용하지 않는다.

## 6. 개발 워크플로우

1. `main`을 최신 상태로 갱신한다.
2. `main`에서 작업 목적에 맞는 브랜치를 생성한다.
3. 작업 브랜치에서 변경을 수행한다.
4. 논리적 단위로 커밋한다.
5. 가능한 범위에서 빌드, 테스트, 린트를 수행한다.
6. 작업 브랜치를 원격 저장소에 push한다.
7. 작업 브랜치에서 `main`으로 PR을 생성한다.
8. PR 내용을 검토하고 병합한다.
9. 병합 후 작업 브랜치를 삭제한다.

## 7. Pull Request 정책

### 7.1 기본 원칙

- PR은 사람 간 승인 절차가 아니라 변경 단위를 검증하고 기록하기 위한 Change Gate로 사용한다.
- PR 제목과 본문은 반드시 한국어로 작성한다.
- PR 제목은 가능하면 `prefix: 한국어 메시지` 형식을 사용한다.
- PR에는 변경 목적, 주요 변경 사항, 검증 결과, 영향 또는 위험 요소를 기록한다.
- 서로 관련 없는 변경은 하나의 PR에 포함하지 않는다.
- 병합 전 충돌 여부와 CI 상태를 확인한다.

### 7.2 PR 본문 권장 형식

```markdown
## 요약

이번 PR에서 수행한 변경 사항을 간략히 설명한다.

## 변경 사항

- 변경 사항 1
- 변경 사항 2
- 변경 사항 3

## 검증

- 빌드 결과
- 테스트 결과
- 린트 결과

## 영향 및 위험

- 기존 기능에 미치는 영향
- 주의가 필요한 사항
```


## 8. 커밋 정책

### 8.1 기본 원칙

- 하나의 커밋은 하나의 논리적 변경 단위를 표현한다.
- 서로 관련 없는 변경을 하나의 커밋에 섞지 않는다.
- 커밋 전 가능한 범위에서 빌드, 테스트, 린트를 수행한다.
- 의미 없는 중간 커밋 메시지를 사용하지 않는다.

### 8.2 커밋 메시지 형식

모든 커밋 메시지는 반드시 다음 형식을 사용한다.

```text
<prefix>: <한국어 메시지>
```

- `prefix`는 영문으로 작성한다.
- 콜론(`:`) 뒤의 변경 내용 설명은 반드시 한국어로 작성한다.
- 메시지는 변경의 목적과 결과가 드러나도록 간결하게 작성한다.

허용하는 기본 prefix:

| Prefix | 용도 |
|---|---|
| `feat` | 신규 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 기능 변경 없는 구조 개선 |
| `docs` | 문서 변경 |
| `test` | 테스트 추가 또는 수정 |
| `chore` | 일반 유지보수 작업 |
| `style` | 포맷, 스타일 등 비기능 변경 |
| `perf` | 성능 개선 |
| `build` | 빌드 시스템 또는 의존성 변경 |
| `ci` | CI/CD 설정 변경 |
| `revert` | 이전 변경 되돌리기 |

예시:

```text
feat: 카메라 촬영 기능 추가
fix: 사진 권한 거부 시 앱 종료 문제 수정
refactor: 이미지 처리 로직 구조 개선
docs: 시스템 설계 문서 업데이트
test: 매직아이 생성 로직 테스트 추가
chore: Flutter 패키지 버전 업데이트
```

금지 예시:

```text
feat: add camera capture
fix: handle permission error
update files
final changes
수정
```


## 9. 릴리스 정책

- `main`의 모든 커밋은 원칙적으로 릴리스 가능한 상태여야 한다.
- 실제 릴리스 시 필요한 경우 Semantic Versioning 기반 Tag를 생성한다.

예시:

```text
v1.0.0
v1.1.0
v1.1.1
```

## 10. Hotfix 정책

S1에서는 별도의 `hotfix/` 흐름을 사용하지 않는다.

긴급 수정도 일반 `fix/` 작업 브랜치를 `main`에서 생성하여 동일한 PR 절차로 처리한다.

## 11. Temporary Branch 정책

S1에서는 `temp/` 브랜치를 표준 정책으로 사용하지 않는다.

작업 중 임시 저장이 필요한 경우 가능한 한 작업 브랜치 내부의 정상 커밋 또는 로컬 Git 기능을 사용한다.

## 12. 금지 사항

- `main` 직접 commit
- `main` 직접 push
- PR 없이 `main` 변경
- 미완성 또는 검증되지 않은 변경의 `main` 병합
- 서로 관련 없는 변경을 하나의 PR에 혼합
- 의미 없는 커밋 메시지 사용
- 영문 변경 설명으로 커밋 메시지 작성
- 영문으로 PR 제목 또는 본문 작성

## 13. AI Agent 규칙

AI Agent는 다음 규칙을 반드시 준수한다.

1. 작업 시작 전 `git status`와 현재 브랜치를 확인한다.
2. 현재 프로젝트에 적용된 Git Strategy Level을 확인한다.
3. 해당 Strategy에서 허용되지 않은 브랜치에 직접 변경을 반영하지 않는다.
4. 기존의 미커밋 변경 사항을 임의로 삭제하거나 덮어쓰지 않는다.
5. 모든 커밋 메시지를 `prefix: 한국어 메시지` 형식으로 작성한다.
6. 커밋 prefix는 영문으로 작성하고 변경 설명은 한국어로 작성한다.
7. 모든 PR 제목과 본문을 한국어로 작성한다.
8. 하나의 커밋과 PR에는 하나의 논리적 작업 단위를 유지한다.
9. PR 생성 전 가능한 범위에서 빌드, 테스트, 린트를 수행한다.
10. 실패한 검증 항목이 있으면 숨기지 않고 PR에 명시한다.
11. unrelated change를 임의로 함께 수정하거나 정리하지 않는다.
12. 작업 완료 후 불필요한 작업 브랜치는 삭제한다.
13. 현재 전략에서 금지된 직접 push를 수행하지 않는다.
14. destructive Git command는 사용자 승인 없이 실행하지 않는다.

특히 다음 명령은 사용자 승인 없이 실행하지 않는다.

```text
git push --force
git push --force-with-lease
git reset --hard
git clean -fd
git branch -D
```

이미 존재하는 다른 작업자의 변경 또는 AI Agent의 이전 작업을 제거할 가능성이 있는 Git 조작은 수행하지 않는다.


## 14. 워크플로우 예시

```text
main
  │
  ├── feature/camera-capture
  │       │
  │       ├── feat: 카메라 촬영 기능 추가
  │       └── fix: 촬영 실패 예외 처리 추가
  │
  └<──── PR ──── feature/camera-capture
```

## 15. 요약

```text
작업 브랜치
     │
     PR
     ↓
    main
```

S1의 핵심은 **단순한 브랜치 구조를 유지하면서 `main`만은 반드시 PR로 보호하는 것**이다.

## 공통 언어 규칙

Git의 구조적 식별자는 영문을 사용하고, 사람이 읽는 변경 설명은 한국어를 사용한다.

- 브랜치 prefix: 영문
- 커밋 prefix: 영문
- 커밋 설명: 한국어
- PR 제목: 한국어
- PR 본문: 한국어
